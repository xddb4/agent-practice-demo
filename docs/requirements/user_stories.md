# StudyPilot 用户故事与验收标准

> 能力与时间规划智能体 | 依据项目 README 核心能力（两层任务组织、四象限判定、证据链能力评估、个性化推荐）编写，遵循 INVEST 原则，验收标准采用 Gherkin 语法

---

## 故事 1　录入目标与固定日程，生成当天计划

**用户故事：**

- **角色：** 作为一名课程、科研与生活任务交织的本科生，
- **功能：** 我想要录入目标、任务和固定日程后一键生成当天计划（固定任务时间轴 + 非固定任务建议时段），
- **价值：** 以便无需手工排程就知道今天每个时段做什么，且固定安排不被打乱。

**验收标准（Gherkin）：**

```gherkin
场景: 正常生成包含固定时间轴的当天计划
  Given 用户已录入固定日程"08:00–09:40 数据库课程"，以及非固定任务"完成实验报告"（预计 90 分钟，今天 18:00 截止）
  When 用户打开"今日计划"页面
  Then 系统应先锁定固定任务生成时间轴，再在剩余可用时间内为非固定任务分配建议时段
  And 任何非固定任务不得占用固定时段，且不产生固定时间冲突
  And 页面顶部应显示今日可用时间、已安排时长与未安排时长

场景: 固定时间冲突被拦截
  Given 日历中已存在固定事件"16:30 实验室例会"
  When 用户录入与之重叠的固定事件"16:00–17:00 导师汇报"并保存
  Then 系统应阻止保存，并提示冲突的事件名称与重叠时间段
  And 已生成的当天计划不应被自动改动
```

## 故事 2　四象限自动判定与用户覆盖

**用户故事：**

- **角色：** 作为需要快速判断"先做什么"的本科生，
- **功能：** 我想要系统自动判定任务的重要/紧急四象限并说明依据，同时允许我手动修改，
- **价值：** 以便减少人工分类成本，同时保留最终决定权。

**验收标准（Gherkin）：**

```gherkin
场景: 自动判定并展示依据
  Given 用户创建任务"周五 16:00 导师汇报"，系统识别到截止时间、目标关联和影响范围
  When 任务保存成功
  Then 系统应将其判定为"重要且紧急"，并展示判定依据
  And 任务应出现在右侧四象限区域对应的方块中，且每日计划中保留象限标签

场景: 用户覆盖判定
  Given 任务"阅读论文"已被系统判定为"不重要不紧急"
  When 用户将其拖入"重要不紧急"方块
  Then 系统应更新该任务象限，并把本次覆盖记录为偏好信号
  And 该修改不得直接改变任何能力分数
```

## 故事 3　每日任务排序与手动调整

**用户故事：**

- **角色：** 作为正在执行当天计划的本科生，
- **功能：** 我想要非固定任务默认按 DDL 从近到远排序，并支持手动拖动和一键恢复默认排序，
- **价值：** 以便默认顺序合理，又能按当天实际情况灵活调整执行顺序。

**验收标准（Gherkin）：**

```gherkin
场景: 默认 DDL 排序
  Given 今日非固定任务：A（DDL 今天 18:00，重要且紧急）、B（DDL 今天 18:00，重要不紧急）、C（DDL 明天 12:00，重要不紧急）
  When 用户打开今日计划
  Then 顺序应为 A、B、C（同 DDL 按象限优先级，A 先于 B）
  And 每条任务应显示预计时长、截止时间与四象限标签

场景: 手动拖动后恢复默认排序
  Given 用户已把任务 C 拖动到列表顶部
  When 用户点击"恢复按 DDL 排序"
  Then 列表应恢复为 A、B、C 的默认顺序
  And 本次调整与恢复操作应写入审计日志
```

## 故事 4　能力报告可追溯查看

**用户故事：**

- **角色：** 作为关心科研能力成长的本科生，
- **功能：** 我想要能力报告中的每个分数都能展开查看证据、置信度和变化原因，
- **价值：** 以便能力评估透明可信，而不是一个不可解释的黑盒分数。

**验收标准（Gherkin）：**

```gherkin
场景: 展开查看分数详情
  Given 用户的"实验验证与数据素养"分数最近一次更新使用了 2 条证据
  When 用户点击该分数
  Then 系统应展示证据列表（含来源与时间）、置信度、趋势和本次变化原因
  And 每条证据应可追溯到原始记录（任务复盘或阶段作品）

场景: 证据不足时不提升置信度
  Given 某能力维度当前仅有 1 条单一来源证据
  When 系统执行评估更新
  Then 单次分数变化不得超过规则允许的小幅上限
  And 置信度不得提升，报告应显示"证据不足"提示
```

## 故事 5　个性化机会推荐与确认入计划

**用户故事：**

- **角色：** 作为希望把能力短板转化为具体行动的本科生，
- **功能：** 我想要系统根据能力短板、时间预算和历史成果推荐比赛/课程/项目，并说明理由与投入，
- **价值：** 以便清楚每个建议为什么推荐、训练什么能力、需要多少时间，再决定是否接受。

**验收标准（Gherkin）：**

```gherkin
场景: 生成带理由的推荐
  Given 用户"实验验证与数据素养"维度低于目标要求，且未来两周每天约有 2 小时空闲
  When 系统生成推荐列表
  Then 每条推荐应包含推荐理由、影响的能力维度和预计投入时间
  And 推荐状态应标记为"待确认"，不得直接进入正式计划

场景: 用户认同后加入计划
  Given 用户对某条推荐点击"接受"
  When 系统将其转化为阶段任务
  Then 任务应加入"重要不紧急"象限，并拆分为连续的小任务
  And 用户拒绝的推荐应记录原因并用于后续推荐优化
```

## INVEST 自检说明

- **Independent（独立的）：** 五个故事分别对应计划生成、四象限、排序、能力评估、推荐五个独立模块（tasks/fixed_events、plan_blocks、skill_evaluations、recommendations），可独立开发与验收。
- **Negotiable（可协商的）：** 故事只约束行为与价值，具体 UI（时间轴样式、方块颜色、拖拽交互细节）留给设计与开发协商。
- **Valuable（有价值的）：** 共同覆盖 README 的核心闭环"计划执行—行为证据—能力评估—下一轮建议"，每条都对应可感知的用户价值。
- **Estimable（可估算的）：** 每个故事的输入输出和涉及的数据表明确，便于拆分任务与估算工作量。
- **Small（小巧的）：** 每个故事聚焦单一功能簇，可在一个迭代内完成。
- **Testable（可测试的）：** 每条故事配正向 + 异常/边界两类 Gherkin 场景，可直接转化为自动化验收测试。
