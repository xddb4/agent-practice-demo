## 任务三 团队沟通管理计划

沟通管理目标是让信息在合适的时间到达合适的成员，并形成可追踪的决定和产出。即时通信适合快速同步，正式决策必须回写项目协作平台或文档库。

当前阶段先完成需求拆解、领域模型和系统架构设计；下表的开发、测试、发布和运行维护安排为未来阶段的沟通预案，实际启动时间待确认。需求与产品边界以项目 README 为准，围绕本科生科研成长场景，按“个人计划—能力可视化—反馈与成果分析—个性化机会推荐”分阶段推进。

### 沟通规则

- 会议前：发出议题、背景材料和希望达成的决定；无议题则取消会议。
- 会议中：明确主持人和记录人，争议围绕证据与用户价值展开。
- 会议后：24 小时内发布结论、负责人和截止日期；重要决定纳入决策日志。
- 信息分级：阻塞、安全和发布事故即时通知；一般进度在每日或每周节奏中处理。
- 单一事实源：任务状态进入协作看板，代码进入项目仓库，正式文档进入统一文档库。
- 需求评审：以 README 为基准核对两层任务组织、六维能力模型、固定冲突校验、证据来源及用户确认入口；差异形成变更记录，评估通过后同步相关需求与设计文档。
- 职责评审：排程、四象限和分数更新由确定性规则处理，大模型用于材料解析、解释和候选方案生成；Task Planner 不直接修改能力分数，优先级覆盖只回流为偏好信号。
- 确认与追溯：正常和降级流程均保留用户确认、修改或拒绝提取证据的入口，确认后的提取证据才用于能力评估；机会推荐须经用户认同后加入正式计划。计划调整、能力变化和用户覆盖均保留来源与审计记录。

## 任务三 风险管理计划

### 风险应对措施

| 风险           | 预防措施                                       | 触发条件                                      | 应急措施                                               |
| -------------- | ---------------------------------------------- | --------------------------------------------- | ------------------------------------------------------ |
| 需求频繁变化   | 设立 MVP 边界和需求评分 每次变更评估价值与成本 | 两周内新增高优需求超过 3 项或已确认范围被推翻 | 冻结当前迭代 将变更放入下一周期 由负责人做取舍         |
| 能力指标失真   | 使用六维指标和可解释评分规则，保留证据、置信度、趋势与变化原因；提取证据确认后使用，优先级修改不直接改分 | 用户对画像认可率低于 70%、出现明显刷分或未确认提取证据影响评分 | 暂停受影响评估，排除错误证据，按审计记录复核并重算，显示不确定性，开展人工抽查与规则修订 |
| 排程不可执行   | 固定日历与计划共用数据；先校验并锁定固定任务，再安排非固定任务，预留缓冲并允许用户调整 | 出现固定时间冲突，或连续一周计划完成率低于 50%、改动率过高 | 阻止冲突计划生效并提示调整；说明剩余时长、冲突原因和可延期选项，重估负荷后重排 |
| 模型输出不稳定 | 规则负责排程、四象限和评分；大模型负责解析、解释和候选生成；结构化校验、来源引用与回归评测 | 关键场景评测通过率低于 90%，或出现错误证据、绕过确认或越权修改分数 | 暂停受影响的解析与候选生成，切换规则模板或备用模型；持续保留证据确认与推荐入计划确认，修复后复测 |
| 隐私与数据泄露 | 最小化采集 权限隔离 加密 日志审计和删除机制    | 发现越权访问 异常导出或敏感日志暴露           | 立即隔离服务 撤销凭证 保全日志 通知负责人并按制度处置  |
| 第三方服务中断 | 服务抽象 超时重试 缓存与降级方案               | 连续 5 分钟错误率高于阈值或接口变更           | 切换备用服务 启用本地模板 保存请求待恢复后重试         |
| 模型成本超支   | 上下文压缩 缓存 分级模型 单用户配额            | 周成本超过预算 20% 或单用户成本持续上升       | 限制非核心生成 降级模型 调整频率并复盘高耗场景         |
| 关键成员变动   | 结对工作 文档化 代码评审与权限备份             | 核心岗位缺席超过 3 个工作日                   | 启动替补分工 调整里程碑 缩减非核心范围                 |
| 开发估时偏差   | 拆小任务 加入缓冲 每日更新剩余工作量           | 连续两天燃尽偏离计划 20% 以上                 | 重排优先级 并行处理阻塞 延后后续功能而不压缩测试       |
| 配置管理混乱   | 统一分支策略 环境配置和数据字典 自动化检查     | 合并冲突频发或环境差异导致缺陷                | 冻结合并 指定版本基线 修复配置后再恢复开发             |
| 用户参与不足   | 提前招募 分层邀请 激励与简短反馈机制           | 有效内测用户少于 30 人或周反馈少于 10 条      | 扩大社团和课程渠道 开展引导访谈 提供体验激励           |
| 上线缺陷       | 设置发布门禁 回归测试 灰度发布和回滚演练       | 严重缺陷未清零或核心流程失败                  | 暂停发布或立即回滚 发布故障说明并复盘                  |

### 风险跟踪与升级机制

- 风险登记册由测试与运营负责人维护，每周例会更新概率、影响、责任人、状态和下一步行动。
- 优先权为最高的风险即时升级给产品负责人，并由相关技术负责人共同决定暂停、降级或回滚。
- 风险关闭需具备证据，例如连续两个周期指标恢复正常、缺陷验证通过或替代方案稳定运行。
- 涉及能力评估或推荐的风险，关闭前应验证证据可追溯、用户纠错有效、优先级修改不直接改分、推荐未经认同不入计划，并记录正常与降级流程的验证结果。
- 发生事故后 48 小时内完成无责复盘，记录时间线、根因、影响、修复和预防措施。
