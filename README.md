# StudyPilot：能力与时间规划智能体

这是一个面向本科生科研成长的智能体项目。它把用户的目标、任务、时间投入、阶段成果和自我反馈关联起来，形成“计划执行—行为证据—能力评估—下一轮建议”的闭环。

当前阶段先完成需求拆解、领域模型和系统架构设计，暂不急于实现完整代码。

## 1. 要解决的问题

用户通常拥有零散的课程、科研、竞赛和生活任务，但缺少三种关联：

1. 任务与能力之间没有明确关系，用户不知道某项任务究竟在训练什么。
2. 计划只描述“做什么”，没有根据固定时间、重要性、紧急性和可用精力安排“何时做、做到什么程度”。
3. 能力评价通常依赖主观印象，不能根据任务完成情况、阶段作品、论文结果和用户自述持续修正。

本项目的核心不是普通待办清单，而是一个以时间为主线、以能力成长为创新点的个人科研成长系统。任务组织采用两层结构：第一层用四象限判断优先级，第二层把当天任务分为固定时间点任务和非固定时间点任务。

## 2. 产品目标与边界

### 目标

- 把抽象能力维度转化为可观察、可记录、可解释的指标。
- 根据用户的固定日程和目标生成日计划、周计划和阶段计划。
- 自动判断任务的“重要/紧急”四象限，并允许用户覆盖判断。
- 将行为、成果和反馈转化为能力证据，动态更新能力报告。
- 根据能力短板和未来目标提出课程、竞赛、论文或项目建议。
- 让用户知道每个建议的依据、影响的能力和预计投入时间。

### 暂不纳入第一版

- 自动替用户报名比赛、提交论文或操作外部日历。
- 仅凭一次任务完成情况给出稳定人格结论。
- 将能力分数作为升学、招聘或其他高风险决策的唯一依据。
- 依赖不可解释的黑盒分数替代用户确认。

## 3. 核心用户流程

```text
输入目标/任务/固定日程
        ↓
任务解析与能力关联
        ↓
重要性-紧急性判定 + 用户可调整
        ↓
每日任务分为固定时间点任务与非固定时间点任务
        ↓
按固定时间和可用精力生成计划
        ↓
执行任务并记录完成度、时长、阻塞点
        ↓
提交阶段作品、论文结果或自我叙述
        ↓
提取行为证据并更新能力报告
        ↓
根据能力变化和新目标生成下一轮建议
```

每个智能体建议都应回答四个问题：

- 为什么推荐？
- 它训练或验证哪项能力？
- 需要投入多少时间？
- 用户接受后会怎样改变计划？

## 4. 能力模型

能力模型采用“维度—指标—证据—反馈”的四层结构。第一版建议使用以下六个维度：

| 能力维度 | 可观察指标 | 典型证据 |
| --- | --- | --- |
| 问题发现与研究设计 | 能否提出可验证问题；是否定义变量、基线和评价标准 | 研究计划、实验设计、选题说明 |
| 计算与系统思维 | 能否建立分层模型；能否解释硬件、软件和性能之间的关系 | 系统分析、架构图、代码/电路实验 |
| 实验验证与数据素养 | 是否记录条件；是否进行对照；是否解释异常数据 | 实验日志、数据表、复现实验、结果图 |
| 批判性与独立思考 | 是否质疑结论、工具输出和前提；是否比较替代方案 | 失败记录、反例、方案比较、AI 使用说明 |
| 信息素养与学术规范 | 能否检索、筛选、引用和复述文献；是否遵守数据与学术诚信 | 文献卡片、引用记录、数据来源 |
| 表达、协作与反思 | 能否清楚表达方法与限制；能否吸收反馈并迭代 | 周报、汇报、论文草稿、复盘自述 |

能力分数只作为当前估计，不代表固定标签。建议保存：`score`、`confidence`、`evidence_count`、`last_updated` 和 `trend`。

### 证据权重建议

第一版可以使用可解释的规则，而不是直接训练复杂模型：

- 阶段作品或论文结果：权重 0.35
- 连续行为记录：权重 0.25
- 任务完成质量与复盘：权重 0.20
- 用户自评和自我叙述：权重 0.10
- 用户对系统建议的接受或拒绝：权重 0.10

一次证据只能小幅改变分数；多次同方向证据、不同来源相互印证后，才提高置信度。

## 5. 时间与任务模型

### 两层任务组织方式

四象限和每日任务分类解决的是不同问题，不能互相替代：

| 层次 | 解决的问题 | 示例 |
| --- | --- | --- |
| 四象限 | 这件事优先级如何，应该先处理什么 | 重要且紧急、重要不紧急 |
| 每日任务类型 | 今天具体以什么时间形态执行 | 固定时间点任务、非固定时间点任务 |

固定时间点任务类似上课、会议、实验室例会，具有明确开始时间和结束时间，通常不可自由移动。非固定时间点任务类似完成作业、阅读论文、准备比赛，可以在当天可用时间内安排，系统需要给出建议时间段，但用户可以调整。

任务可以同时拥有两个属性。例如“周五 16:00 的导师汇报”属于“重要且紧急 + 固定时间点任务”；“本周完成实验报告”属于“重要不紧急 + 非固定时间点任务”。

### 任务字段

```json
{
  "id": "task-001",
  "title": "完成缓存实验结果解释",
  "goal_id": "goal-research-01",
  "skills": ["experiment", "critical-thinking"],
  "importance": 5,
  "urgency": 5,
  "quadrant": "important_urgent",
  "daily_task_type": "flexible",
  "estimate_minutes": 90,
  "deadline": "2026-10-17T18:00:00+08:00",
  "fixed_time": {
    "start": null,
    "end": null,
    "location": null,
    "recurrence": null
  },
  "status": "todo",
  "completion": 0,
  "evidence_required": "记录至少一个异常原因和一个验证方案"
}
```

### 四象限规则

- 重要且紧急：优先安排，靠近截止时间，界面强调显示。
- 重要不紧急：放入阶段计划，拆成连续的小任务，保护固定投入时间。
- 不重要但紧急：批量处理，限制占用深度工作时间。
- 不重要不紧急：延后、合并或建议删除。

系统先根据截止时间、目标关联、影响范围和用户输入自动判断，再显示判断依据，用户可以修改。用户的修改应被记录为偏好信号，但不能直接改变能力分数。

### 固定时间与弹性时间

固定课程、会议、实验室例会和睡眠时段进入独立的日历模型，并对应每日任务中的 `fixed` 类型。智能体先放置固定时间点任务，再在剩余时间中安排非固定时间点任务，并预留缓冲时间。固定日程页面和计划页面使用同一份数据，避免重复维护。

### 计划页面布局

计划页面采用“左侧每日计划 + 右侧四象限”的布局。左侧按上下两个区域展示每日任务，右侧独立展示四项划分。每日任务本身仍然保留四象限备注，因此用户可以从执行视角看今天做什么，也可以从优先级视角看任务为什么这样排序。

```text
┌──────────────────────────────┬──────────────┐
│ 每日计划                     │ 四项划分      │
│                              │              │
│ 固定时间点：课表式呈现       │ 重要且紧急    │
│ 08:00 课程                  │ 重要不紧急    │
│ 16:30 实验室例会             │ 不重要但紧急  │
│                              │ 不重要不紧急  │
│ 非固定时间点：任务条目       │              │
│ □ 完成实验报告  [重要不紧急] │              │
│ □ 阅读论文      [重要不紧急] │              │
└──────────────────────────────┴──────────────┘
```

#### 每日计划区域

- **固定时间点任务**：使用类似课程表或时间轴的形式呈现，按开始时间排序，显示时间、任务名称、地点、重复规则和四象限备注。固定任务不可与其他固定任务冲突。
- **非固定时间点任务**：使用上下排列的任务条目呈现，每条显示完成框、任务名称、预计时长、截止时间、能力关联、建议时间段和四象限标签。用户可以拖动或修改建议时间段。
- 每日区域顶部显示日期、可用时间、已安排时长和未安排时长。

#### 右侧四项区域

右侧固定显示四个独立的小方块，每个小方块对应一个象限，并显示象限名称、任务数量、最早 DDL 和任务摘要：重要且紧急、重要不紧急、不重要但紧急、不重要不紧急。四个小方块使用不同的颜色层级，其中“重要且紧急”使用更强的视觉强调。任务可以从右侧小方块拖入每日计划，也可以从每日计划拖回小方块调整优先级。

四项区域用于快速查看和调整优先级，不能替代每日执行列表。每日任务上必须保留象限标签，避免用户在上下文切换后失去任务优先级信息。

#### 条目排序规则

每日计划中的非固定时间点任务默认按照 DDL 从近到远排列，DDL 越近的任务越靠前。相同 DDL 时，按以下顺序排列：重要且紧急、重要不紧急、不重要但紧急、不重要不紧急；同一象限内再按预计耗时从长到短排列。用户可以手动拖动调整当天执行顺序，但系统应保留“按 DDL 排序”的恢复操作。

固定时间点任务按开始时间排序，不参与非固定任务的 DDL 排序。右侧四个小方块中的任务也默认按 DDL 从近到远排列。

排程顺序建议为：先校验固定时间冲突，再锁定固定时间点任务，最后为非固定时间点任务分配建议时间块。非固定任务无法全部安排时，应说明剩余时长、冲突原因和可延期选项。四项区域中的排序仍然影响每日非固定任务的默认顺序，但用户可以手动调整。

## 6. 推荐智能体架构

建议采用“规则引擎 + 结构化模型 + 大模型解释”的混合架构：

```text
前端 Web / 移动端
        ↓
API 层：用户、任务、日历、反馈、报告
        ↓
领域服务
  ├─ Task Planner：任务拆解、排程、四象限
  ├─ Skill Mapper：任务与能力指标映射
  ├─ Evidence Extractor：从作品、自述、日志提取证据
  ├─ Assessment Engine：分数、置信度、趋势更新
  ├─ Recommendation Engine：比赛/课程/项目推荐
  └─ Feedback Loop：完成情况与用户修正回流
        ↓
数据层：关系数据库 + 文档存储 + 向量检索（后续）
```

### 模块职责

**Task Planner** 负责时间可行性和计划质量，不能直接修改能力分数。

**Skill Mapper** 维护任务、行为和能力指标的映射，输出“这项任务为什么能训练该能力”。

**Evidence Extractor** 从阶段作品、论文结果和用户自述中提取可引用的证据片段，并保留原文来源。

**Assessment Engine** 使用可解释规则更新分数和置信度，记录每次变化的原因。

**Recommendation Engine** 根据目标、能力短板、时间预算和外部机会生成候选建议，必须等待用户认同后才加入正式计划。

**Feedback Loop** 收集完成度、延期、跳过、用户修改优先级和建议接受度，用于优化计划和个人偏好。

## 7. 推荐数据表

第一版关系数据库可以包含以下表：

- `users`：用户与时区、作息、方向。
- `goals`：长期目标、阶段目标、截止时间。
- `tasks`：任务、优先级、估时、状态和能力关联。
- `fixed_events`：固定课程、会议、例会和不可用时段。
- `plan_blocks`：实际排入日历的时间块。
- `skills`：能力维度与指标定义。
- `skill_evaluations`：分数、置信度、趋势和更新时间。
- `evidence`：行为、作品、自述、论文结果等证据及来源。
- `feedback`：用户反馈、系统分析和处理状态。
- `recommendations`：推荐内容、理由、用户是否接受。
- `audit_logs`：计划调整、能力变化和用户覆盖判断的记录。

## 8. MVP 分阶段实现

### 阶段一：可用的个人计划

- 用户创建目标、任务和固定日程。
- 任务四象限自动判断与手动修改。
- 每日任务明确区分固定时间点任务和非固定时间点任务。
- 先安排固定时间点任务，再安排非固定时间点任务。
- 生成当天计划和固定日历。
- 支持完成、延期、跳过和复盘。

验收标准：用户能在 3 分钟内输入一个目标，并得到包含固定任务时间轴和非固定任务建议时段的当天计划；系统不能生成固定时间冲突。

### 阶段二：能力可视化

- 建立六个能力维度和指标字典。
- 任务创建时选择或自动推荐能力关联。
- 根据完成质量和复盘记录生成能力报告。
- 每个分数显示证据、置信度和变化原因。

验收标准：任何能力分数都能追溯到至少一条用户可查看的证据。

### 阶段三：反馈与成果分析

- 支持上传或粘贴阶段作品、论文结果和自我叙述。
- 抽取问题、方法、实验、结果、限制和反思等结构化信息。
- 允许用户确认、修改或拒绝系统提取的证据。
- 将确认后的证据回流能力报告和计划建议。

验收标准：用户可以纠正系统错误，错误不会直接污染后续能力评估。

### 阶段四：个性化机会推荐

- 输入比赛、课程、项目或论文机会。
- 对照用户能力、时间预算和历史成果给出匹配理由。
- 用户认同后，生成备赛或准备阶段任务并加入“重要不紧急”。
- 根据计划完成度重新评估推荐可行性。

验收标准：推荐必须包含理由、预计投入、影响能力和用户确认步骤。

## 9. 首选技术方案

如果以 Web 应用起步，建议采用：

- 前端：React + TypeScript + Vite，日历和图表使用成熟组件。
- 后端：FastAPI 或 NestJS，按领域模块拆分 API。
- 数据库：PostgreSQL，任务、日程、能力和证据使用结构化表。
- 文档与文件：对象存储保存原始作品，数据库保存解析结果和引用位置。
- 智能体编排：先使用显式工作流；只有在需要理解自然语言材料时调用大模型。
- 检索：第二阶段再加入向量检索，优先检索用户自己的资料和已确认证据。

初期不建议把所有逻辑交给大模型。排程、四象限和分数更新应由确定性代码完成，大模型负责解析、解释和生成候选方案。

## 10. 论文依据如何落地

两篇参考论文共同强调：学习行为可以作为能力发展的外显证据；高阶认知、计算思维、硬件/系统思维、批判性思维、实验验证、反思和积极学习习惯与学习成果和科研素养有关；人工智能时代的培养应采用分层递进、项目驱动、批判性思维贯穿和人机协同的方式。

因此，本项目不把“完成任务”直接等同于“能力提升”，而是要求记录过程证据，例如问题是否清晰、是否设置基线、是否解释异常、是否比较方案、是否反思 AI 输出和是否根据反馈迭代。

## 11. 开发顺序建议

先实现领域模型、四象限规则和两类每日任务，再做固定日历与非固定任务排程；随后加入能力指标与证据链，最后接入大模型解析和机会推荐。每一步都保留用户确认入口、来源记录和审计日志，确保系统的建议可解释、可纠正、可回溯。
